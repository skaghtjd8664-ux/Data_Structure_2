# 과제 15: 퀵 정렬과 AVL 트리 정렬 성능 비교

## 1. 실험 개요

같은 무작위 정수 데이터를 두 가지 방법으로 정렬된 상태로 만들고, 그 상태에서 삽입·삭제를 반복했을 때의 **실행 시간**, **비교 횟수**, **데이터 이동 횟수**, **메모리 사용량**을 비교하였다.

| 방법 | 초기 정렬 | 삽입·삭제 | 최종 정렬 결과 |
|---|---|---|---|
| Quick Sort | 배열을 퀵 정렬 | 정렬된 배열에서 이진 탐색으로 위치를 찾고 원소를 밀고 당김 | 배열 그 자체 |
| AVL Tree | 모든 값을 AVL 트리에 삽입하고 중위 순회 | AVL 트리에 삽입·삭제 후 회전으로 균형 유지 | 중위 순회 결과 |

실험 조건은 다음과 같다.

- 데이터 크기 `n`: 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 값 범위: 0 이상 1,000,000 이하의 정수 (중복 허용)
- 삽입·삭제 작업 수: `n / 5`회 (삽입과 삭제는 각각 1/2 확률)
- 작업 목록은 측정 전에 한 번 만들고, 두 방법에 **같은 순서로 똑같이** 적용

---

## 2. 구현 내용

### 2.1 퀵 정렬 + 정렬된 배열

- **퀵 정렬**: Hoare 분할을 사용하고, 현재 구간의 가운데 원소를 피벗으로 선택한다.
- **삽입**: 이진 탐색(`lower_bound`)으로 넣을 위치를 찾고, 그 뒤의 원소를 모두 한 칸씩 오른쪽으로 민 뒤 값을 넣는다.
- **삭제**: 이진 탐색으로 값의 위치를 찾고, 그 뒤의 원소를 모두 한 칸씩 왼쪽으로 당긴다.

배열은 이미 정렬되어 있으므로 위치는 이진 탐색으로 찾았다. 선형 탐색을 쓰면 배열 방식의 비교 횟수가 불필요하게 커져서, 배열 방식의 진짜 비용인 **원소 이동**을 공정하게 비교할 수 없기 때문이다.

### 2.2 AVL 트리

- 각 노드는 `key`, `count`, `height`, `left`, `right`를 저장한다. 같은 값이 다시 들어오면 새 노드를 만들지 않고 `count`를 1 늘린다.
- 삽입·삭제 후 되돌아오면서 각 노드의 높이를 갱신하고, 좌우 높이 차이가 2 이상이면 LL, LR, RR, RL 회전으로 균형을 맞춘다.
- 삭제할 노드에 자식이 둘이면, 오른쪽 서브트리의 최솟값 노드(후속자)를 떼어내 그 값을 옮겨오고 후속자 노드를 해제한다.
- 정렬 결과는 중위 순회로 배열에 기록한다. `count`가 2 이상인 노드는 그 횟수만큼 기록한다.

### 2.3 삽입·삭제 작업 생성

각 작업은 1/2 확률로 삽입 또는 삭제이다.

- **삽입**: 0~1,000,000 사이의 무작위 값을 넣는다.
- **삭제**: 그 시점에 데이터에 **실제로 들어 있는 값** 중 하나를 무작위로 골라 삭제한다.

삭제할 값을 0~1,000,000에서 그냥 무작위로 고르면, 데이터가 최대 2만 개뿐이라 그 값이 들어 있을 확률이 2% 이하이다. 그러면 삭제가 거의 일어나지 않아 삭제 성능을 측정할 수 없다. 그래서 작업을 만들 때 현재 데이터 목록을 따로 관리하여, 삭제는 항상 존재하는 값을 대상으로 하였다. 작업 생성은 측정 구간 밖에서 미리 수행한다.

### 2.4 난수 생성과 재현성

splitmix64 의사난수 생성기를 직접 구현하여 데이터, 작업 종류, 삽입 값, 삭제 대상을 만들었다. 시드를 `SEED`(기본값 `20261118`)로 고정했으므로 **비교 횟수, 이동 횟수, 메모리, 최종 개수는 어느 환경에서 실행해도 똑같이 재현**된다. 실행 시간만 환경에 따라 달라진다.

### 2.5 검증

각 데이터 크기에서 다음을 모두 확인하였고, 모든 크기에서 통과하였다.

- 초기 정렬 결과와 최종 결과가 오름차순인지
- 두 방법의 초기 정렬 결과와 최종 결과가 **원소 하나까지 완전히 같은지** (`memcmp`)
- 최종 원소 개수가 작업 목록으로 계산한 예상 개수와 같은지
- 모든 삭제가 실제로 성공했는지 (실패하면 프로그램이 오류를 출력하고 종료)

## 3. 측정 기준

### 3.1 측정 단계

두 방법을 같은 세 단계로 나누어 각각 측정하고, 합계를 전체 결과로 사용하였다.

| 단계 | Quick Sort | AVL Tree |
|---|---|---|
| Initial Sort | 퀵 정렬 | `n`번 삽입으로 트리 구성 + 중위 순회로 정렬 결과 출력 |
| Operations | `n/5`번 배열 삽입·삭제 | `n/5`번 트리 삽입·삭제 |
| Final Output | 없음 (배열이 이미 정렬 결과) | 중위 순회로 최종 정렬 결과 출력 |

### 3.2 비교 횟수

데이터 값끼리 실제로 비교한 횟수를 모두 센다.

- 퀵 정렬: 분할에서 원소와 피벗을 비교한 횟수
- 배열 삽입·삭제: 이진 탐색의 비교, 삭제 시 찾은 값이 맞는지 확인하는 비교
- AVL: 탐색 경로에서 키를 비교한 횟수 (`key < node`가 거짓이면 `key > node`를 한 번 더 비교하므로 노드당 1~2회)

인덱스 비교, 반복문 종료 조건, 높이 비교(균형 판단)는 제외하였다.

### 3.3 데이터 이동 횟수

데이터 값을 대입한 횟수를 센다.

- 배열 원소 대입 1회 = 1, 교환 = 3
- AVL: 새 노드에 키를 저장 1회 = 1, 삭제 시 후속자의 값을 옮겨오는 것 = 1, 중위 순회로 결과 배열에 쓰는 것 = 1
- AVL의 `count` 증감, 포인터 연결 변경, 회전은 데이터 값을 옮기는 것이 아니므로 제외하였다. 회전은 별도로 센다.

### 3.4 실행 시간

- 같은 데이터로 20회 실행한 평균이다. 각 단계를 20회 묶어서 측정하므로 `clock()`의 해상도 문제(Windows는 1ms)를 피할 수 있다.
- 데이터 생성, 작업 생성, 배열 복사, 정렬 검증, 결과 출력은 측정에서 제외하였다.
- AVL의 노드 할당(`malloc`)과 해제(`free`)는 AVL이 반드시 필요로 하는 작업이므로 포함하였다. 마지막에 트리 전체를 해제하는 것은 측정 밖이다.

### 3.5 메모리 사용량

입력 원본 배열과 검증용 결과 배열은 제외하고, **데이터를 보관하는 자료구조 + 재귀 스택**을 같은 기준으로 계산하였다.

```text
Quick Sort : 배열 용량 (n + n/5) × 4 bytes + 퀵 정렬 최대 재귀 깊이 × 8 bytes
AVL Tree   : 실행 중 최대 노드 수 × 32 bytes + AVL 최대 재귀 깊이 × 8 bytes
```

- 배열은 삽입에 대비해 `n + n/5`칸을 미리 할당하므로 그 용량을 그대로 계산하였다.
- AVL 노드 하나는 `int` 3개(12B) + 정렬 여백(4B) + 포인터 2개(16B) = **32바이트**이다 (64비트 환경).
- 재귀 1단계는 다시 돌아와 처리할 정보, 즉 퀵 정렬은 구간 `(low, high)`(8B), AVL은 노드 포인터(8B)를 기억해야 한다고 보았다.
- `malloc`이 내부적으로 쓰는 관리 정보와 실제 함수 프레임 크기는 컴파일러마다 다르므로 제외하였다. 따라서 실제 사용량은 이보다 조금 크다.

## 5. 결과 분석

### 5.1 전체 결과: `n = 1,000`에서는 배열, 그 이상에서는 AVL이 빨랐다

4.1에서 `n = 1,000`일 때는 Quick 방식이 약 9% 빨랐지만, `n = 2,000`부터는 AVL이 빨랐고 그 차이는 크기가 커질수록 벌어졌다 (20,000에서 약 5.6배).

데이터 크기가 2배가 될 때 전체 시간이 몇 배로 늘었는지 보면 원인이 드러난다.

| 크기 변화 | Quick 전체 | Quick 작업 단계 | AVL 전체 | `n log n` 예상 | `n²` 예상 |
|---|---:|---:|---:|---:|---:|
| 1,000 → 2,000 | 3.12배 | 3.26배 | 2.20배 | 2.20배 | 4배 |
| 2,000 → 4,000 | 3.50배 | 3.81배 | 2.25배 | 2.18배 | 4배 |
| 4,000 → 8,000 | 3.58배 | 3.78배 | 2.38배 | 2.17배 | 4배 |
| 8,000 → 16,000 | 3.53배 | 3.66배 | 2.33배 | 2.15배 | 4배 |
| 16,000 → 20,000 | 1.56배 | 1.57배 | 1.27배 | 1.28배 | 1.56배 |

AVL은 `n log n`처럼 늘었지만, Quick 방식의 작업 단계는 `n²`에 가깝게 늘었다. 작업 수가 `n/5`로 `n`에 비례하고, 작업 한 번의 비용도 `n`에 비례하기 때문이다 (5.3). 그래서 `n`이 커질수록 작업 단계가 Quick 방식의 전체 시간을 지배하여, 20,000에서는 전체 시간의 약 96%를 차지하였다.

### 5.2 초기 정렬 단계: 비교 횟수는 같지만 AVL이 약 3배 느리다

| n | Quick 비교 | AVL 비교 | Quick 시간 | AVL 시간 | AVL / Quick 시간 |
|---:|---:|---:|---:|---:|---:|
| 1,000 | 12,954 | 12,945 | 0.0782 | 0.2913 | 3.73배 |
| 8,000 | 142,952 | 141,918 | 1.0999 | 3.1069 | 2.82배 |
| 20,000 | 385,634 | 388,954 | 3.0015 | 8.7446 | 2.91배 |

두 방법의 비교 횟수는 거의 같았다 (`n log₂ n`의 약 1.29~1.38배). 이동 횟수는 오히려 AVL이 훨씬 적었다. 그런데도 AVL이 약 2.8~3.7배 느렸다. **비교와 이동 외의 비용**이 AVL에 많기 때문이다.

- **노드 할당**: 고유 값마다 `malloc`을 한 번씩 호출한다 (20,000에서 약 2만 번). 퀵 정렬은 할당이 없다.
- **포인터 따라가기**: 트리를 내려갈 때마다 다음 노드의 주소를 읽어야 다음 위치를 알 수 있다. 노드들은 메모리 여기저기에 흩어져 있다. 반면 퀵 정렬은 연속된 배열을 앞뒤에서 차례로 읽는다.
- **되돌아오며 균형 유지**: 삽입할 때마다 경로의 모든 노드에서 높이를 다시 계산하고 균형을 검사한다. 회전도 자주 일어난다. 20,000에서는 트리 구성과 작업 전체에서 15,855번, 삽입·삭제 1회당 평균 약 0.66번 회전하였다.
- **중위 순회**: 정렬 결과를 얻으려면 트리 전체를 한 번 더 순회해야 한다.

즉, 한 번에 정렬만 할 때는 배열 + 퀵 정렬이 확실히 유리하다.

### 5.3 삽입·삭제 단계: 배열은 `O(n)`, AVL은 `O(log n)`

20,000 기준, 작업 1회당 평균값은 다음과 같다.

| 항목 | 배열 | AVL |
|---|---:|---:|
| 비교 횟수 | 14.9회 | 21.1회 |
| 이동 횟수 | 9,941회 | 0.69회 |
| 시간 | 16.60μs | 0.66μs |

**배열은 비교는 적지만 이동이 엄청나게 많다.**

- 이진 탐색 덕분에 비교는 작업당 약 `log₂ n + 0.5`회로 AVL보다도 적었다.
- 하지만 위치를 찾은 뒤 그 뒤의 원소를 모두 밀거나 당겨야 한다. 삽입·삭제 위치는 무작위이므로 평균적으로 배열의 절반을 옮긴다. 실제 측정값도 모든 크기에서 작업당 이동 횟수가 `n/2`와 거의 같았다 (20,000에서 9,941회, `n/2` = 10,000).
- 그래서 작업 1회의 비용이 `O(n)`이고, 크기가 커질수록 AVL과의 차이가 커졌다. 작업 1회 시간의 비율(배열 / AVL)은 1,000에서 4.6배, 20,000에서 25.0배였다.

**AVL은 높이만큼만 내려간다.**

- 트리 높이가 약 `log₂ n`이므로 비교는 경로를 따라 노드당 1~2회, 작업당 약 21회였다.
- 원소를 옮기지 않고 포인터만 바꾸므로 이동은 거의 없다. 이동은 새 노드에 키를 넣거나 삭제 때 후속자 값을 옮길 때만 생긴다.

이 결과는 **비교 횟수가 성능을 결정하지 않는다**는 것을 보여준다. 전체 비교 횟수는 모든 크기에서 Quick 방식이 AVL보다 적었지만, 이동 횟수가 수십~수백 배(1,000에서 약 37배, 20,000에서 약 639배) 많아서 `n ≥ 2,000`에서는 더 느렸다.

### 5.4 손익분기점: 작업이 몇 번 이상이면 AVL이 유리한가

AVL은 초기 정렬에서 손해를 보고, 작업 단계에서 이득을 본다. 그래서 작업 수 `k`가 어느 값을 넘으면 AVL이 더 빨라진다.

```text
AVL이 유리해지는 작업 수 k* = (AVL 초기 정렬 + AVL 최종 출력 − Quick 초기 정렬)
                             ÷ (배열 작업 1회 시간 − AVL 작업 1회 시간)
```

4.2의 측정값으로 계산하면 다음과 같다.

| n | AVL의 추가 초기 비용 | 작업 1회 시간 차이 | 손익분기 작업 수 `k*` | `k*` / `n` | 이 실험의 작업 수 (`n/5`) | 결과 |
|---:|---:|---:|---:|---:|---:|---|
| 1,000 | 0.2237ms | 0.96μs | 234회 | 23.4% | 200회 | 배열이 빠름 |
| 2,000 | 0.4523ms | 1.70μs | 267회 | 13.3% | 400회 | AVL이 빠름 |
| 4,000 | 0.9501ms | 3.39μs | 280회 | 7.0% | 800회 | AVL이 빠름 |
| 8,000 | 2.2792ms | 6.69μs | 341회 | 4.3% | 1,600회 | AVL이 빠름 |
| 16,000 | 5.4175ms | 12.57μs | 431회 | 2.7% | 3,200회 | AVL이 빠름 |
| 20,000 | 6.7308ms | 15.93μs | 422회 | 2.1% | 4,000회 | AVL이 빠름 |

- `n = 1,000`에서는 손익분기점(234회)이 실제 작업 수(200회)보다 커서 배열이 빨랐다. 4.1의 결과와 정확히 맞는다.
- 크기가 커질수록 손익분기점의 비율이 23.4%에서 2.1%로 빠르게 줄었다. AVL의 추가 초기 비용은 `n log n`에 비례해 늘지만, 배열의 작업 1회 비용은 `n`에 비례해 늘기 때문이다.
- 즉, **데이터가 클수록 아주 적은 수의 삽입·삭제만 있어도 AVL이 유리해진다.** 20,000개에서는 전체 데이터의 약 2%인 422번만 넘어도 AVL이 더 빨랐다.

### 5.5 컴파일러 최적화에 따른 변화

같은 코드를 `-O2`로 컴파일하면 결과가 달라졌다.

| n | Quick 전체(ms) | AVL 전체(ms) | 더 빠른 방법 |
|---:|---:|---:|---|
| 1,000 | 0.0667 | 0.1380 | 배열 |
| 2,000 | 0.2160 | 0.3314 | 배열 |
| 4,000 | 0.6714 | 0.7780 | 배열 |
| 8,000 | 2.1897 | 1.9552 | AVL |
| 16,000 | 7.4297 | 4.9133 | AVL |
| 20,000 | 11.3246 | 6.1071 | AVL |

20,000에서 배열의 작업 단계는 66.39ms → 9.68ms로 약 6.9배 빨라졌지만, AVL의 작업 단계는 2.66ms → 1.51ms로 약 1.8배만 빨라졌다. 배열의 원소 밀기는 단순한 연속 메모리 복사라서 컴파일러가 아주 효율적인 코드로 바꿀 수 있다. 반면 AVL의 포인터 따라가기와 균형 조정은 최적화로 줄이기 어렵다.

그 결과 손익분기점도 20,000 기준 약 422회(2.1%)에서 약 1,444회(7.2%)로 늘어, 4,000 이하에서는 배열이 더 빨랐다. **어느 방법이 빠른지는 데이터 크기, 작업 비율, 실행 환경에 따라 달라진다.** 다만 크기가 커질수록 AVL이 유리해진다는 경향은 두 경우 모두 같았다. 배열의 작업 비용이 `O(n)`이라는 사실은 최적화로 바뀌지 않기 때문이다.

### 5.6 메모리: AVL이 약 6.6배 더 사용한다

모든 크기에서 AVL은 배열 방식의 약 6.56~6.65배 메모리를 사용하였다 (20,000에서 635,280B 대 96,264B).

- 배열은 값 하나에 4바이트만 쓴다.
- AVL 노드는 값 하나를 저장하기 위해 `count`, `height`, 자식 포인터 2개까지 함께 저장하므로 32바이트를 쓴다. 값 하나당 8배이다.
- 실제 비율이 8배보다 작은 것은 두 가지 이유 때문이다. 첫째, 중복 값이 한 노드로 합쳐져 노드 수가 원소 수보다 적다 (20,000에서 19,823개 노드 / 19,986개 원소). 둘째, 배열은 삽입에 대비해 `n/5`칸을 여유로 더 할당했다.
- 재귀 스택은 두 방법 모두 수백 바이트 이하로, 전체에서 차지하는 비중이 매우 작다.

또한 AVL에서 정렬된 배열 형태의 결과가 필요하면, 중위 순회 결과를 담을 배열이 추가로 필요하다는 점도 고려해야 한다.

### 5.7 AVL 트리의 균형 확인

| n | 노드 수 | 측정한 높이 | 완전 균형일 때 최소 높이 `⌈log₂(노드+1)⌉` | AVL 이론상 최대 높이 `≈ 1.44 log₂(노드+2)` |
|---:|---:|---:|---:|---:|
| 1,000 | 1,002 | 12 | 10 | 14.0 |
| 4,000 | 4,013 | 14 | 12 | 16.9 |
| 20,000 | 19,823 | 17 | 15 | 20.2 |

측정한 높이는 모든 크기에서 최소 높이보다 2 정도 높고, AVL의 이론상 최대 높이보다 낮았다. 따라서 삽입·삭제를 반복한 뒤에도 회전이 균형을 제대로 유지하였다. 높이가 `log n`에 묶여 있기 때문에 작업 1회의 비교 횟수가 `n`이 20배가 되어도 14.7회에서 21.1회로 조금만 늘었다.

참고로 퀵 정렬의 최대 재귀 깊이(20,000에서 33)는 AVL 높이보다 깊었다. 가운데 피벗이 항상 정확한 중앙값은 아니라서 분할이 완벽하게 균형적이지는 않기 때문이다.

## 6. 결론

### 6.1 항목별 비교

| 기준 | 유리한 방법 | 근거 |
|---|---|---|
| 한 번 정렬만 할 때 | Quick (배열) | 비교 횟수는 같지만 AVL은 할당·포인터·균형 비용으로 약 3배 느림 |
| 삽입·삭제 1회 | AVL | 배열은 평균 `n/2`개를 옮겨야 함 (`O(n)`), AVL은 `O(log n)` |
| 전체 (이번 실험, `n/5`회 작업) | `n ≥ 2,000`에서 AVL | 20,000에서 AVL이 약 5.6배 빠름 |
| 메모리 | Quick (배열) | AVL 노드는 값 하나당 8배 공간, 실제 약 6.6배 |

### 6.2 복잡도 정리

| 방법 | 초기 정렬 | 삽입·삭제 1회 | 추가 공간 |
|---|---|---|---|
| 퀵 정렬 + 정렬된 배열 | 평균 `O(n log n)`, 최악 `O(n²)` | 탐색 `O(log n)` + 이동 `O(n)` | 배열 `O(n)` + 평균 스택 `O(log n)` |
| AVL 트리 | `O(n log n)` + 중위 순회 `O(n)` | `O(log n)` | 노드 `O(n)` (값당 32B) + 스택 `O(log n)` |

### 6.3 정리

- **비교 횟수만으로는 성능을 판단할 수 없다.** 배열 방식은 전체 비교 횟수가 더 적었지만, 원소를 밀고 당기는 이동 때문에 크기가 커질수록 크게 느려졌다.
- **정렬을 한 번만 하거나 변경이 드물면** 배열 + 퀵 정렬이 빠르고 메모리도 적게 쓴다.
- **정렬된 상태에서 삽입·삭제가 반복되면** AVL이 유리하다. 데이터가 클수록 손익분기점이 낮아져, 20,000개에서는 작업이 약 2%(최적화 시 약 7%)만 넘어도 AVL이 빨랐다.
- 어느 쪽이 빠른지는 데이터 크기, 작업 비율, 실행 환경에 따라 달라지므로, 실제 상황에 맞게 측정해 보고 선택해야 한다.
