# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교

## 1. 실험 개요

동일한 무작위 정수 데이터에 대해 퀵 정렬의 피벗 선택 방법만 바꾸어 숫자 비교 횟수를 측정하고, 피벗 선택이 분할 결과와 성능에 미치는 영향을 분석하였다.

- 피벗 선택 방법: 첫 번째 원소(First), 무작위 원소(Random), 세 원소의 중앙값(Median-of-Three)
- 데이터 크기: 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터 범위: 0 이상 1,000,000 이하의 정수 (중복 허용)
- 정렬 방향: 오름차순
- 각 데이터 크기에서 세 방법은 **같은 원본 배열의 복사본**을 정렬한다.

과제에서 요구한 단일 실행 결과와 함께, 우연에 의한 편차를 줄이기 위해 **크기마다 100회 반복한 평균**도 측정하였다. 또한 First 방식의 약점을 확인하기 위해 이미 정렬된 입력에 대한 추가 실험을 수행하였다.

---

## 2. 구현 내용

### 2.1 공통 분할 알고리즘

세 방법은 `choose_pivot_index()`에서 피벗 위치를 고르는 부분만 다르고, 이후 분할은 모두 같은 Lomuto 분할을 사용한다.

1. 선택한 피벗을 구간의 마지막 위치로 옮긴다.
2. 구간의 나머지 원소를 하나씩 피벗과 비교하여, 피벗 이하인 원소를 앞쪽으로 모은다.
3. 피벗을 경계 위치로 옮기고, 피벗의 왼쪽과 오른쪽 구간을 각각 다시 정렬한다.

### 2.2 피벗 선택 방법

| 방법 | 선택 방식 |
|---|---|
| First | 현재 구간의 첫 번째 원소 |
| Random | 분할할 때마다 현재 구간에서 무작위 위치를 새로 선택 |
| Median-of-Three | 첫 번째, 가운데(`low + (high - low) / 2`), 마지막 원소 중 크기가 가운데인 값 |

Median-of-Three는 세 값의 산술평균이 아니라 크기순으로 나열했을 때 가운데 값을 고른다. 예를 들어 `10, 50, 30`이면 피벗은 `30`이다. 중앙값은 2~3회의 비교로 결정한다.

### 2.3 난수 생성

C 표준 `rand()`는 `RAND_MAX`가 플랫폼마다 다르다. Windows(MSVC)에서는 32,767이므로 `rand() % 1000001`로는 0~1,000,000 범위를 고르게 만들 수 없다. 그래서 splitmix64 의사난수 생성기를 직접 구현하여 데이터 생성과 무작위 피벗 선택에 사용하였다.

시드를 `SEED`(기본값 `20261105`)로 고정했기 때문에 운영체제나 컴파일러가 달라도 **비교 횟수 결과가 항상 같게 재현**된다. 다른 데이터로 실험하려면 `-DSEED=값`으로 컴파일하면 된다.

### 2.4 정렬 검증

모든 정렬 결과에 대해 다음을 검사하였다.

- 오름차순 여부 (`is_sorted`)
- 세 피벗 방법의 정렬 결과가 서로 완전히 같은지 (`memcmp`)

하나라도 실패하면 프로그램은 오류 메시지를 출력하고 종료한다. 6가지 크기 × 3가지 방법 × 100회 반복의 모든 정렬이 통과하였다.

## 5. 결과 분석

### 5.1 데이터 크기 증가에 따른 비교 횟수 변화

100회 평균을 기준으로, 데이터 크기가 늘어날 때 비교 횟수가 몇 배로 늘었는지 계산하면 다음과 같다.

| 크기 변화 | First | Random | Median-3 | `n log n` 예상 | `n²` 예상 |
|---|---:|---:|---:|---:|---:|
| 1,000 → 2,000 | 2.29배 | 2.25배 | 2.23배 | 2.20배 | 4배 |
| 2,000 → 4,000 | 2.20배 | 2.23배 | 2.19배 | 2.18배 | 4배 |
| 4,000 → 8,000 | 2.21배 | 2.21배 | 2.19배 | 2.17배 | 4배 |
| 8,000 → 16,000 | 2.17배 | 2.17배 | 2.16배 | 2.15배 | 4배 |
| 16,000 → 20,000 | 1.29배 | 1.29배 | 1.28배 | 1.28배 | 1.56배 |

데이터가 2배가 될 때 비교 횟수는 4배가 아니라 2배보다 조금 더 늘었다. 이는 `n log n`이 예측하는 증가율과 거의 일치한다. 따라서 무작위 입력에서 세 방법 모두 평균 `O(n log n)`으로 동작하였다.

비교 횟수를 `n log₂ n`으로 나눈 값도 First와 Random은 약 1.09~1.19, Median-3는 약 1.08~1.12로 일정한 범위에 머물렀다. 크기가 커질수록 이 값이 조금씩 올라가는 것은 작은 구간에서의 효과(구간 크기 2~3에서는 비교가 거의 없음)가 상대적으로 줄어들기 때문이며, 극한에서는 이론값(Random 피벗 약 1.39, Median-of-Three 약 1.19)에 가까워진다.

### 5.2 피벗 선택 방법별 성능 차이

100회 평균에서 Median-of-Three가 **모든 데이터 크기에서 가장 적은 비교 횟수**를 기록하였다. First 대비 감소율은 다음과 같으며, 데이터가 클수록 차이가 커졌다.

| 크기 | 1,000 | 2,000 | 4,000 | 8,000 | 16,000 | 20,000 |
|---|---:|---:|---:|---:|---:|---:|
| Median-3의 감소율 (First 대비) | 1.0% | 3.6% | 4.0% | 4.8% | 5.1% | 6.3% |

반면 First와 Random은 모든 크기에서 차이가 1.4% 이내로, 사실상 같은 성능을 보였다.

### 5.3 피벗 선택이 분할 결과와 비교 횟수에 영향을 미치는 이유

**(1) 한 번의 분할 비용은 같고, 분할 횟수와 깊이가 달라진다**

Lomuto 분할은 피벗이 무엇이든 길이 `m`인 구간에서 정확히 `m - 1`번 비교한다. 따라서 전체 비교 횟수는 "각 원소가 몇 단계의 분할에 참여하는가", 즉 분할 트리의 깊이로 결정된다.

- 피벗이 구간을 반씩 나누면 깊이가 약 `log₂ n`이 되어 전체 비교는 약 `n log₂ n`이다.
- 피벗이 최솟값이나 최댓값이면 구간이 1개만 줄어들어 깊이가 `n`이 되고, 전체 비교는 약 `n² / 2`이다.

결국 피벗이 구간의 중앙값에 가까울수록 비교 횟수가 줄어든다.

**(2) 무작위 데이터에서 First와 Random이 같은 이유**

무작위 데이터에서 첫 번째 원소는 그 자체로 무작위 값이다. 즉, 구간 안에서의 순위가 고르게 분포한다. 따라서 First와 Random은 피벗의 순위 분포가 같고, 기댓값도 같다. 이 경우 기대 비교 횟수의 이론식은 `C(n) = 2(n+1)H(n) - 4n` (`H(n)`은 조화수)이며, 측정값과 비교하면 다음과 같다.

| 크기 | 이론값 | First 평균 | Random 평균 |
|---:|---:|---:|---:|
| 1,000 | 10,986 | 10,895.9 | 10,960.5 |
| 8,000 | 121,051 | 121,094.3 | 121,350.2 |
| 20,000 | 339,250 | 340,470.7 | 339,651.9 |

세 값이 1% 이내로 일치하므로, 무작위 입력에서 First와 Random의 차이는 우연에 의한 것임을 알 수 있다.

**(3) 입력에 패턴이 있으면 First가 무너진다**

4.4의 정렬된 입력 실험에서 First는 크기 1,000에서 약 50만 번(`n² / 2`), 4,000에서 약 800만 번을 비교하였다. 크기가 2배가 될 때마다 비교 횟수가 약 4배로 늘어 `O(n²)`이 되었다. 정렬된 구간의 첫 번째 원소는 항상 최솟값이므로, 매번 구간이 1개씩만 줄어들기 때문이다.

반면 Random은 입력 순서와 상관없이 무작위 위치를 고르므로 무작위 입력과 비슷한 비교 횟수를 유지하였다. Median-of-Three는 정렬된 구간의 가운데 원소가 정확한 중앙값이 되므로 오히려 무작위 입력보다 적게 비교하였다. 즉, First가 무작위 데이터에서 잘 동작한 것은 입력이 무작위였기 때문이며, 피벗 선택 자체가 좋은 것은 아니다.

**(4) Median-of-Three가 비교를 줄이는 원리와 그 비용**

세 원소의 중앙값은 극단값이 될 확률이 낮고 구간의 중앙 근처에 몰리므로 분할이 더 균형 있게 이루어진다. 4.3의 분해 결과에서 크기 20,000일 때 이 효과를 확인할 수 있다.

- 분할 호출 수: 13,335.1회 → 11,449.2회 (약 14% 감소)
- 분할 비교 횟수: 340,470.7회 → 288,996.2회 (약 15% 감소)

그러나 Median-of-Three는 분할할 때마다 중앙값을 정하기 위해 평균 약 2.6회를 더 비교한다. 이 비용이 30,086.1회로, 분할 비교 감소분(약 51,500회)의 절반 이상을 차지하였다. 특히 크기 2~3인 작은 구간에서도 중앙값 비교를 수행하므로, 이득은 거의 없고 비용만 발생한다. 그 결과 최종 감소율은 15%가 아니라 6.3%에 그쳤다. 크기 1,000처럼 작은 데이터에서는 작은 구간의 비중이 커서 감소율이 1.0%에 불과하였다.

### 5.4 단일 실행에서 결과가 뒤바뀌는 이유

4.1의 단일 실행에서는 1,000·2,000·8,000에서 First가, 20,000에서 Median-3가 가장 적게 비교하는 등 크기마다 순위가 달랐다. 이는 피벗 선택의 효과가 아니라 **실행마다 생기는 편차** 때문이다.

무작위 피벗 퀵 정렬의 비교 횟수 표준편차는 약 `0.65n`으로 알려져 있다. 크기 20,000에서는 약 13,000회로, 평균의 약 3.8%에 해당한다. Median-3의 평균적인 이점(약 6%)과 비슷한 크기이므로, 한 번의 실행만으로는 순위가 쉽게 뒤바뀐다. 100회 평균을 내자 순위가 모든 크기에서 Median-3 < Random ≈ First로 일관되게 나타났다.

### 5.5 가장 효과적인 피벗 선택 방법

실험 결과 **Median-of-Three가 가장 효과적**이었다.

- 무작위 입력: 100회 평균에서 모든 크기에서 가장 적게 비교하였고, 크기가 클수록 이점이 커졌다 (20,000에서 6.3% 감소).
- 정렬된 입력: First는 `O(n²)`으로 무너졌지만 Median-of-Three는 가장 적은 비교 횟수를 유지하였다.

Random은 비교 횟수 면에서 First와 같지만, 입력 순서에 영향을 받지 않는다는 안정성이 장점이다. First는 무작위 입력에서는 문제가 없으나, 정렬되었거나 거의 정렬된 입력에서 최악의 성능을 보이므로 실제로 사용하기에는 위험하다.

## 6. 보너스: 재귀적 퀵 정렬과 반복적 퀵 정렬

### 6.1 구현

- **재귀적 방법**: 분할 후 왼쪽 구간과 오른쪽 구간에 대해 함수를 다시 호출한다. 구간 정보는 함수 호출 스택에 저장된다.
- **반복적 방법**: 처리할 구간 `(low, high)`를 직접 만든 배열 스택에 저장하고, 스택이 빌 때까지 꺼내어 분할한다.
  - 두 하위 구간 중 **큰 구간을 먼저 넣고 작은 구간을 나중에 넣어**, 작은 구간부터 처리한다. 이렇게 하면 스택 깊이가 약 `log₂ n` 이하로 제한된다.
  - 따라서 크기 64의 고정 배열로 충분하며, 측정 구간 안에서 `malloc`/`free`가 발생하지 않는다.

두 방법은 같은 Median-of-Three 피벗 선택과 같은 분할 함수를 사용한다. 실제로 두 방법의 비교 횟수가 149,824회로 완전히 같았으므로, **같은 분할을 같은 횟수만큼 수행**했음을 확인하였다.

### 6.2 측정 방법

- 데이터 크기 10,000, 피벗 Median-of-Three, 같은 원본 데이터 사용
- 같은 원본의 복사본 100개를 **측정 전에 미리 준비**하고, 정렬 100회만 연속으로 측정하여 1회 평균을 구했다. 따라서 데이터 생성, 배열 복사, 결과 출력 시간은 측정에 포함되지 않는다.
- `clock()`의 해상도 문제를 피하기 위해 정렬 100회를 한꺼번에 측정하였다.
- 측정 전에 워밍업 실행을 1회 수행하고, 측정 순서에 따른 편향을 줄이기 위해 두 라운드에서 재귀·반복의 순서를 바꾸어 평균을 냈다.

### 6.3 결과

측정 환경: Intel Xeon 2.80GHz, Linux, gcc 13.3.0, `-std=c11` (최적화 옵션 없음)

```text

Pivot     : Median-of-Three
Repeats   : 100 sorts x 2 rounds (order alternated)

Recursive Quick Sort : 0.8999 ms
Iterative Quick Sort : 0.8844 ms
Comparisons          : 149824 / 149824 (identical)
Sorted Check         : PASS
```

프로그램을 5번 실행한 결과, 매번 재귀적 방법이 2~5% 정도 빠르게 나타났다. 참고로 `-O2` 최적화를 적용하면 두 방법 모두 약 0.6ms로 빨라졌고, 실행할 때마다 순위가 바뀔 만큼 차이가 사라졌다.

### 6.4 분석

**(1) 차이가 작은 이유**

두 방법은 같은 분할을 같은 횟수만큼 수행하며, 실행 시간의 대부분은 분할 함수 안의 비교와 교환이 차지한다. 두 방법이 다른 부분은 "다음에 처리할 구간을 어떻게 기억하는가"뿐이므로, 전체 시간에서 차지하는 비중이 작다.

**(2) 재귀가 오히려 조금 빨랐던 이유**

흔히 반복적 방법이 함수 호출 오버헤드가 없어 빠르다고 하지만, 이번 구현에서는 그렇지 않았다.

- 함수 호출은 CPU가 직접 지원하는 동작(`call`/`ret`, 스택 포인터 이동)이라 비용이 매우 작다.
- 반복적 방법도 구간을 스택에 넣을 때마다 `push_range` 함수를 호출하고, 두 구간의 크기를 비교하는 분기와 배열 인덱스 계산, 메모리 읽기·쓰기를 추가로 수행한다.
- 최적화 없이 컴파일하면 이 추가 작업들이 그대로 실행되므로, 함수 호출을 없앤 이득보다 구간 관리 비용이 조금 더 컸다.
- `-O2`에서는 컴파일러가 `push_range` 같은 작은 함수를 인라인하고 변수를 레지스터에 둘 수 있으므로 두 방법의 차이가 측정 오차 수준으로 줄어들었다.

**(3) 반복적 방법의 실제 장점은 속도가 아니라 안전성이다**

재귀적 방법의 재귀 깊이는 분할 결과에 따라 결정되며, 최악의 경우 `n`까지 깊어진다. 예를 들어 First 피벗으로 정렬된 데이터 20,000개를 정렬하면 재귀 깊이가 약 20,000이 되어, 스택 크기가 작은 환경에서는 스택 오버플로가 발생할 수 있다. 반면 이번 반복적 구현은 작은 구간을 먼저 처리하므로 입력과 관계없이 스택 깊이가 약 `log₂ n` 이하로 제한된다.

## 7. 결론

- 무작위 입력에서 세 방법 모두 데이터가 2배가 될 때 비교 횟수가 약 2.2배로 늘어 `O(n log n)`으로 동작하였다.
- 퀵 정렬의 비교 횟수는 피벗이 만드는 분할의 균형, 즉 분할 트리의 깊이에 의해 결정된다.
- 무작위 입력에서 First와 Random은 피벗의 순위 분포가 같으므로 비교 횟수가 이론값과 함께 사실상 같았다.
- First는 정렬된 입력에서 `O(n²)`으로 무너져, 입력 패턴에 매우 민감하다는 것을 확인하였다.
- Median-of-Three는 분할 비교를 약 15% 줄였지만, 중앙값 결정 비용 때문에 최종적으로 약 6%를 줄였다. 그래도 모든 크기와 입력에서 가장 효과적이었다.
- 단일 실행은 편차 때문에 순위가 뒤바뀔 수 있으므로, 피벗 방법을 비교할 때는 반복 평균이 필요하다.
- 재귀적·반복적 퀵 정렬은 같은 분할을 수행하므로 실행 시간 차이가 몇 % 이내로 작았다. 반복적 방법의 실질적인 장점은 스택 깊이를 제한할 수 있다는 점이다.
