# 과제 14: 힙 정렬, 퀵 정렬 및 병합 정렬 성능 비교

## 1. 실험 개요

동일한 무작위 정수 데이터에 대해 힙 정렬, 병합 정렬, 퀵 정렬을 수행하고 **숫자 비교 횟수**, **실행 시간**, **알고리즘별 추가 메모리 사용량**을 비교하였다. 퀵 정렬은 피벗 선택 방법에 따라 세 가지로 나누어 측정하였다.

| 알고리즘 | 설명 |
|---|---|
| Heap Sort | 최대 힙을 이용한 힙 정렬 |
| Merge Sort | 하향식(재귀) 병합 정렬 |
| Quick (First) | 첫 번째 원소를 피벗으로 사용 |
| Quick (Random) | 무작위 원소를 피벗으로 사용 |
| Quick (Median3) | 첫 번째·가운데·마지막 원소의 중앙값을 피벗으로 사용 |

실험 조건은 다음과 같다.

- 데이터 크기: 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터 범위: 0 이상 1,000,000 이하의 정수 (중복 허용), 오름차순 정렬
- 각 크기에서 하나의 원본 배열을 만들고, **같은 원본의 복사본**을 다섯 알고리즘에 제공

과제 출력 외에, 우연에 의한 편차를 줄이기 위한 **100회 반복 평균**과, 입력 상태에 따른 차이를 확인하기 위한 **이미 정렬된 입력** 실험을 추가로 수행하였다.

## 2. 구현 내용

### 2.1 힙 정렬

1. **힙 구성**: 마지막 내부 노드(`n/2 - 1`)부터 루트까지 거꾸로 올라가며 `sift_down`을 수행하여 배열 전체를 최대 힙으로 만든다.
2. **추출**: 루트(최댓값)를 힙의 마지막 원소와 교환하고, 힙 크기를 1 줄인 뒤 루트에서 다시 `sift_down`을 수행한다. 이를 힙 크기가 1이 될 때까지 반복한다.

`sift_down`은 부모와 두 자식 중 가장 큰 값을 찾기 위해 한 단계마다 최대 2번 비교하고, 부모가 가장 크면 멈춘다. 재귀 대신 반복문으로 구현하였으므로 재귀 호출 스택을 쓰지 않는다.

### 2.2 병합 정렬

구간을 항상 가운데에서 둘로 나누어 각각 재귀적으로 정렬한 뒤, 두 정렬된 부분을 임시 배열 `temp`에 병합하고 원래 배열로 다시 복사한다. 임시 배열은 정렬 시작 시 `n`개 크기로 한 번만 할당한다.

### 2.3 퀵 정렬

세 방법은 피벗 선택만 다르고, 분할은 모두 같은 Lomuto 분할을 사용한다. 선택한 피벗을 구간의 마지막으로 옮긴 뒤, 피벗 이하인 원소를 앞쪽으로 모으고 피벗을 경계 위치에 놓는다. Median-of-Three는 세 값 중 크기가 가운데인 값을 2~3회 비교로 고른다.

### 2.4 난수 생성과 재현성

C 표준 `rand()`는 `RAND_MAX`가 플랫폼마다 다르다(Windows는 32,767). 그래서 splitmix64 의사난수 생성기를 직접 구현하여 데이터 생성과 무작위 피벗 선택에 사용하였다. 시드를 `SEED`(기본값 `20261116`)로 고정했으므로 **비교 횟수, 이동 횟수, 메모리 값은 어느 환경에서 실행해도 똑같이 재현**된다. 실행 시간만 환경에 따라 달라진다.

### 2.5 정렬 검증

모든 정렬 결과에 대해 오름차순 여부를 검사하고, 다섯 알고리즘의 결과 배열이 서로 완전히 같은지도 `memcmp`로 확인하였다. 하나라도 실패하면 프로그램은 오류를 출력하고 종료한다. 6가지 크기 × 5가지 알고리즘 × 100회의 모든 정렬이 통과하였다.

## 3. 측정 기준

### 3.1 비교 횟수

| 알고리즘 | 포함하는 비교 |
|---|---|
| 힙 정렬 | `sift_down`에서 부모와 자식 원소의 값을 비교한 횟수 |
| 병합 정렬 | 병합 과정에서 두 부분 배열의 원소끼리 비교한 횟수 |
| 퀵 정렬 | 분할 과정에서 원소와 피벗을 비교한 횟수 |
| Median-of-Three | 위에 더해, 중앙값을 결정하기 위한 비교 |

인덱스 비교, 반복문 종료 조건, 자식 존재 여부 검사, 무작위 위치 생성, 배열 복사, 데이터 생성은 제외하였다.

### 3.2 실행 시간

- 같은 원본의 복사본 50개를 **측정 전에 미리 준비**하고, 정렬 50회만 연속으로 측정한 뒤 1회 평균을 구했다.
- 따라서 데이터 생성, 배열 복사, 정렬 검증, 결과 출력 시간은 측정에서 제외된다.
- `clock()`은 해상도가 낮아(Windows는 1ms) 작은 데이터를 1회만 재면 `0`이나 `1`로 나올 수 있다. 50회를 묶어 측정하여 이 문제를 피했다.
- 병합 정렬의 임시 배열 `malloc`/`free`는 병합 정렬이 반드시 필요로 하는 작업이므로 측정에 포함하였다. 80KB 할당·해제는 1회 약 0.00002ms로 정렬 시간에 비해 무시할 수 있다.

### 3.3 추가 메모리

원본 배열과 정렬용 복사 배열은 모든 알고리즘에 공통이므로 제외하고, **다섯 알고리즘에 같은 기준**을 적용하였다.

```text
추가 메모리 = 보조 배열 크기 + 최대 재귀 깊이 × 8 bytes
```

- **보조 배열**: 병합 정렬은 임시 배열 `n × sizeof(int)`, 힙 정렬과 퀵 정렬은 0
- **재귀 1단계당 8바이트**: 재귀 호출 한 단계가 나중에 처리할 구간 정보 `(low, high)`, 즉 `int` 2개(`sizeof(Range)`)를 기억해야 한다고 보았다. 재귀 대신 명시적 스택을 쓸 때 저장해야 하는 정보와 같은 양이다.
- **최대 재귀 깊이**: 첫 호출을 1단계로 보고, 크기 1 이하라서 바로 반환하는 호출까지 포함해 가장 깊었던 단계를 기록하였다. 힙 정렬은 재귀를 쓰지 않으므로 0이다.

힙 정렬의 값 0은 "메모리를 전혀 쓰지 않는다"는 뜻이 아니다. 힙 정렬도 `root`, `child`, `pick` 같은 지역 변수 몇 개는 사용한다. 다만 이 공간은 데이터 크기 `n`과 관계없이 일정하므로(`O(1)`), 데이터 크기에 따라 늘어나는 보조 공간만 비교하는 이 기준에서는 0으로 나타난다.

실제 함수 호출 프레임에는 복귀 주소, 다른 매개변수 등이 더 들어가므로 실제 스택 사용량은 이보다 크고 컴파일러마다 다르다. 따라서 이 값은 알고리즘이 논리적으로 필요로 하는 최소 공간이며, 모든 알고리즘에 같은 기준을 적용했으므로 서로 비교하기에는 공정하다.

### 3.4 분석용 추가 지표

- **이동 횟수**: 데이터 대입 1회를 1로 계산한다. 교환은 임시 변수를 거치므로 3회로 계산하였다.
- **호출 횟수**: 병합·퀵 정렬은 재귀 함수 호출 횟수, 힙 정렬은 `sift_down` 호출 횟수
- **힙 정렬 단계별 비교**: 힙 구성 단계와 추출 단계의 비교 횟수를 나누어 기록하였다.

## 5. 결과 분석

### 5.1 데이터 크기 증가에 따른 변화

100회 평균 비교 횟수를 기준으로, 데이터 크기가 늘 때 비교 횟수가 몇 배로 늘었는지 계산하면 다음과 같다.

| 크기 변화 | Heap | Merge | Quick (First) | Quick (Random) | Quick (Median3) | `n log n` 예상 | `n²` 예상 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 1,000 → 2,000 | 2.24배 | 2.23배 | 2.25배 | 2.23배 | 2.21배 | 2.20배 | 4배 |
| 2,000 → 4,000 | 2.21배 | 2.21배 | 2.22배 | 2.23배 | 2.21배 | 2.18배 | 4배 |
| 4,000 → 8,000 | 2.19배 | 2.19배 | 2.19배 | 2.20배 | 2.17배 | 2.17배 | 4배 |
| 8,000 → 16,000 | 2.18배 | 2.17배 | 2.20배 | 2.19배 | 2.17배 | 2.15배 | 4배 |
| 16,000 → 20,000 | 1.28배 | 1.28배 | 1.29배 | 1.29배 | 1.28배 | 1.28배 | 1.56배 |

다섯 알고리즘 모두 데이터가 2배가 될 때 비교 횟수가 4배가 아니라 약 2.2배로 늘었다. 이는 `n log n`의 예상 증가율과 거의 같으므로, 무작위 입력에서 모두 `O(n log n)`으로 동작하였다.

차수가 같으므로 차이는 앞에 붙는 상수에서 나온다. 비교 횟수를 `n log₂ n`으로 나눈 값은 다음과 같다.

| 알고리즘 | `비교 횟수 / (n log₂ n)` |
|---|---:|
| Merge Sort | 0.87 ~ 0.91 |
| Quick (Median3) | 1.09 ~ 1.12 |
| Quick (First), Quick (Random) | 1.11 ~ 1.19 |
| Heap Sort | 1.69 ~ 1.79 |

### 5.2 비교 횟수: 병합 < 퀵 < 힙

100회 평균에서 모든 크기의 순위가 **병합 < Median3 < First ≈ Random < 힙**으로 같았다. 힙 정렬은 병합 정렬의 1.94~1.96배, Median3의 1.55~1.60배를 비교하였다.

**(1) 힙 정렬이 가장 많이 비교하는 이유**

4.3을 보면 힙 정렬 비교의 약 89~93%가 **추출 단계**에서 나온다.

- 추출할 때마다 힙의 마지막 원소가 루트로 올라온다. 이 원소는 힙의 맨 아래층에 있던 값이라 대체로 작으므로, 다시 거의 맨 아래까지 내려가야 한다.
- 한 층 내려갈 때마다 "왼쪽 자식과 비교, 오른쪽 자식과 비교"로 **2번씩** 비교한다.
- 따라서 원소 하나를 추출할 때 약 `2 × (힙의 높이)`번 비교하게 된다. 측정한 추출 단계 비교는 `1.50 ~ 1.66 × n log₂ n`이었다. `2 × n log₂ n`보다 작은 이유는 추출이 진행될수록 힙이 작아져 높이가 낮아지기 때문이다.

반면 **힙 구성 단계**는 모든 크기에서 약 `1.86n ~ 1.88n`번으로 `n`에 정비례하였다(`O(n)`). 아래층 노드는 내려갈 거리가 짧고, 그런 노드가 대부분이기 때문이다. 그래서 크기가 커질수록 힙 구성의 비중은 11.1%에서 7.4%로 줄었다.

**(2) 병합 정렬이 가장 적게 비교하는 이유**

- 병합 정렬은 값과 관계없이 항상 정확히 반으로 나누므로 재귀 깊이가 `⌈log₂ n⌉ + 1`로 고정된다 (4.2에서 11, 12, …, 16).
- 길이 `m`인 구간을 병합할 때 비교는 최대 `m - 1`번이고, 한쪽이 먼저 바닥나면 나머지는 비교 없이 복사된다.
- 비교 한 번마다 원소 하나가 병합 결과에 자리를 잡으므로, 힙처럼 한 원소를 내리기 위해 층마다 두 번씩 비교하는 일이 없다.

**(3) 퀵 정렬이 중간인 이유**

퀵 정렬의 분할은 구간의 모든 원소를 피벗과 한 번씩 비교한다. 피벗이 구간을 정확히 반으로 나누는 경우가 드물어, 크기 20,000에서 최대 깊이가 First·Random 약 34, Median3 약 26으로 병합 정렬(16)보다 깊었다. 그만큼 원소가 거치는 단계가 많아 병합 정렬보다 22~31% 더 비교하였다. Median3는 분할이 더 균형적이어서 세 퀵 정렬 중 가장 적게 비교하였다.

### 5.3 실행 시간: 퀵 < 병합 < 힙

4.1의 실행 시간 순위는 모든 크기에서 **퀵 정렬(가장 빠른 방식) < 병합 정렬 < 힙 정렬**이었다.

| 크기 | 1,000 | 2,000 | 4,000 | 8,000 | 16,000 | 20,000 |
|---|---:|---:|---:|---:|---:|---:|
| 가장 빠른 퀵 정렬 | Median3 | Median3 | Median3 | First | First | Median3 |
| 병합이 가장 빠른 퀵보다 느린 정도 | 44% | 29% | 29% | 26% | 36% | 24% |
| 힙이 병합보다 느린 정도 | 10% | 22% | 35% | 38% | 37% | 52% |
| 힙이 가장 빠른 퀵보다 느린 정도 | 59% | 58% | 75% | 74% | 87% | 89% |

**(1) 힙 정렬이 가장 느린 이유: 작업량 자체가 가장 많다**

크기 20,000의 100회 평균에서 힙 정렬은 비교 횟수(510,768)와 이동 횟수(805,232)가 모두 다섯 알고리즘 중 가장 많았다. 이동 횟수는 병합 정렬의 1.40배, Median3의 1.61배였다. 원소가 한 층 내려갈 때마다 교환(3회 이동)이 일어나기 때문이다.

흥미롭게도 비교 1회당 시간은 힙 정렬(약 9.5ns)이 병합 정렬(약 12.2ns)보다 짧았다(20,000 기준). 즉 힙 정렬은 연산 하나하나가 느린 것이 아니라 **해야 할 연산이 많아서** 느리다. 그래서 비교 횟수는 병합 정렬의 약 2배인데 시간 차이는 10~52%에 그쳤다.

또한 힙 정렬은 부모 `i`에서 자식 `2i + 1`로 이동하므로, 힙이 클수록 한 번에 멀리 떨어진 메모리로 뛰어다닌다. 이 접근 방식은 연속된 메모리를 차례로 읽는 병합·퀵 정렬보다 캐시 효율이 낮다고 알려져 있다. 이번 실험에서도 크기가 커질수록 힙과 병합의 시간 차이가 10%에서 52%로 커졌는데, 이 경향과 맞는다. 다만 이번 데이터는 최대 80KB로 작아서, 캐시의 영향을 다른 요인과 분리해 측정하지는 못했다.

**(2) 병합 정렬이 퀵 정렬보다 느린 이유: 비교 외의 부가 작업**

병합 정렬은 비교 횟수가 퀵 정렬보다 적은데도 24~44% 느렸다. 비교 1회당 시간도 다섯 알고리즘 중 가장 길었다.

- **이동**: 각 단계에서 모든 원소를 `temp`에 쓰고 다시 원래 배열로 복사한다. 이동 횟수가 입력과 관계없이 고정되어 있으며(1,000에서 100회 모두 19,952회), Median3보다 약 15% 많았다.
- **호출**: 크기 1인 구간까지 모두 나누므로 호출 횟수가 정확히 `2n - 1`이다 (20,000에서 39,999회). Median3(22,903.5회)의 약 1.75배이다.
- **반복문**: 원소마다 병합 반복문과 복사 반복문을 두 번 거치고, 두 배열(원래 배열과 `temp`)을 오간다.

**(3) 퀵 정렬 세 방식의 차이**

가장 빠른 퀵 정렬은 크기에 따라 Median3(4개 크기)와 First(2개 크기)가 번갈아 나타났다. 무작위 입력에서는 First의 첫 원소도 무작위 값이라 Median3와 큰 차이가 없기 때문이다. Random은 16,000을 제외한 모든 크기에서 퀵 정렬 중 가장 느렸다. 분할할 때마다 64비트 곱셈과 나눗셈으로 난수를 만드는 비용이 들기 때문이다. 이 비용은 비교 횟수에는 들어가지 않지만 실행 시간에는 포함된다.

**최적화를 켜도 순위는 같았다**

`-O2`로 컴파일하면 크기 20,000에서 힙 2.10ms, 병합 1.73ms, Median3 1.39ms로 모두 빨라졌지만 순위는 그대로였다. 따라서 이 차이는 알고리즘 구조에서 나온 것이다.

### 5.4 추가 메모리: 힙 `O(1)` < 퀵 `O(log n)` < 병합 `O(n)`

| 알고리즘 | 크기 20,000의 추가 메모리 | 1,000 → 20,000 증가 | 공간 복잡도 |
|---|---:|---|---|
| Heap Sort | 0 B | 변화 없음 | `O(1)` |
| Quick (Median3) | 207.4 B | 136.4 → 207.4 B (약 1.5배) | 평균 `O(log n)` |
| Quick (First) | 272.2 B | 175.3 → 272.2 B (약 1.6배) | 평균 `O(log n)` |
| Merge Sort | 80,128 B | 4,088 → 80,128 B (약 19.6배) | `O(n)` |

- **힙 정렬**은 입력 배열 안에서 힙을 만들고, `sift_down`을 반복문으로 구현하여 재귀도 쓰지 않는다. 데이터 크기와 관계없이 지역 변수 몇 개만 사용한다.
- **퀵 정렬**은 보조 배열은 없지만 재귀 깊이만큼 공간이 필요하다. 데이터가 20배 커져도 공간은 약 1.5~1.6배만 늘어 `log n`에 비례하였다.
- **병합 정렬**은 임시 배열이 `n`에 비례하여, 데이터가 20배 커지자 공간도 약 20배 늘었다.

### 5.5 이미 정렬된 입력에서의 변화

4.4의 결과는 입력 상태에 따라 성능이 얼마나 흔들리는지를 보여준다.

- **힙 정렬은 거의 변하지 않았다.** 정렬된 입력의 비교 횟수는 무작위 평균보다 약 4% 많았을 뿐이고, 크기가 2배가 될 때 2.21~2.23배로 늘어 여전히 `O(n log n)`이었다. 오름차순 배열로 최대 힙을 만들면 작은 값이 위에 있어 힙 구성 때 조금 더 내려가야 하지만, 추출 단계는 힙이 만들어진 뒤에 진행되므로 원래 입력 순서의 영향을 거의 받지 않기 때문으로 보인다.
- **병합 정렬은 오히려 빨라졌다.** 정렬된 입력에서는 왼쪽 부분이 항상 먼저 바닥나므로 병합 비교가 절반으로 줄어든다. 크기 1,000의 비교 횟수가 8,706.4회(무작위 평균)에서 5,044회로 줄었다.
- **Quick (First)는 `O(n²)`으로 무너졌다.** 크기 1,000의 비교 횟수 499,500회는 정확히 `n(n-1)/2`이다. 정렬된 구간의 첫 원소는 항상 최솟값이라서 구간이 한 칸씩만 줄어들기 때문이다. 크기 4,000에서는 병합 정렬보다 약 46배 느렸고, 재귀 깊이가 3,997이 되어 추가 메모리(31,976B)도 병합 정렬(16,104B)보다 커졌다.
- **Random과 Median3는 무너지지 않았다.** Median3는 정렬된 구간의 가운데 원소가 정확한 중앙값이 되므로 다섯 알고리즘 중 가장 빨랐다.

## 6. 결론

### 6.1 항목별 비교

| 기준 | 가장 우수 | 가장 불리 | 근거 |
|---|---|---|---|
| 비교 횟수 | 병합 정렬 | 힙 정렬 | 힙은 원소 하나를 내릴 때 층마다 2번 비교, 병합의 약 1.95배 |
| 실행 시간 (무작위) | 퀵 정렬 (Median3, First) | 힙 정렬 | 힙은 비교·이동 모두 가장 많음, 병합은 복사·호출 부담 |
| 추가 메모리 | 힙 정렬 | 병합 정렬 | 힙 `O(1)`, 퀵 `O(log n)`, 병합 `O(n)` |
| 입력 상태에 대한 안정성 | 힙·병합 정렬 | Quick (First) | 힙·병합은 정렬된 입력에서도 `O(n log n)` 유지 |

### 6.2 복잡도 정리

| 알고리즘 | 평균 시간 | 최악 시간 | 추가 공간 | 안정 정렬 |
|---|---|---|---|---|
| 힙 정렬 | `O(n log n)` | `O(n log n)` | `O(1)` | 아니요 |
| 병합 정렬 | `O(n log n)` | `O(n log n)` | `O(n)` | 예 |
| 퀵 정렬 | `O(n log n)` | `O(n²)` | 평균 `O(log n)`, 최악 `O(n)` | 아니요 |

(안정 정렬 여부는 이번 실험에서 측정하지 않은, 알고리즘의 일반적인 성질이다.)

### 6.3 정리

- 다섯 알고리즘 모두 무작위 입력에서 `O(n log n)`으로 동작했지만, 차수가 같을 때는 **상수와 부가 작업**이 실제 성능을 결정하였다.
- **비교 횟수만으로 속도를 판단할 수 없다.** 병합 정렬은 비교가 가장 적었지만 복사와 호출 부담 때문에 퀵 정렬보다 느렸다. 힙 정렬은 연산 1회당 비용은 낮았지만, 비교와 이동이 모두 가장 많아 가장 느렸다.
- **힙 정렬**은 최악의 경우에도 `O(n log n)`이 보장되고 추가 메모리가 `O(1)`인 유일한 알고리즘이다. 대신 평균 속도가 가장 느리다. 메모리가 매우 제한되거나 최악의 경우를 반드시 피해야 할 때 적합하다.
- **병합 정렬**은 입력과 관계없이 성능이 일정하고 안정 정렬이지만, `O(n)` 메모리가 필요하다.
- **퀵 정렬**은 평균적으로 가장 빠르고 메모리도 적게 쓰지만 피벗 선택에 따라 `O(n²)`으로 무너질 수 있다. Median-of-Three 같은 좋은 피벗 전략과 함께 써야 한다.

## 7. 컴파일 및 실행

```bash
gcc -Wall -Wextra -Werror -std=c11 Heap_Quick_Merge_Compare.c -o Heap_Quick_Merge_Compare
./Heap_Quick_Merge_Compare
```

다른 데이터로 실험하려면 `-DSEED=12345`처럼 시드를 지정하여 컴파일한다. 시드가 같으면 비교 횟수, 이동 횟수, 메모리 값은 어느 환경에서나 같게 나오고, 실행 시간만 환경에 따라 달라진다.
