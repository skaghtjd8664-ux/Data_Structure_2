# 과제 13: 병합 정렬과 퀵 정렬의 성능 비교

## 1. 실험 개요

동일한 무작위 정수 데이터에 대해 병합 정렬과 퀵 정렬을 수행하고, **숫자 비교 횟수**, **실행 시간**, **알고리즘별 추가 메모리 사용량**을 비교하였다.

퀵 정렬은 다음 세 가지 피벗 선택 방법으로 구현하였다.

- 첫 번째 원소 선택 (First)
- 무작위 원소 선택 (Random)
- 세 원소의 중앙값 선택 (Median-of-Three)

실험 조건은 다음과 같다.

- 데이터 크기: 1,000 / 2,000 / 4,000 / 8,000 / 16,000 / 20,000
- 데이터 범위: 0 이상 1,000,000 이하의 정수 (중복 허용), 오름차순 정렬
- 각 크기에서 하나의 원본 배열을 만들고, **같은 원본의 복사본**을 네 알고리즘에 제공

과제에서 요구한 실행 결과 외에, 우연에 의한 편차를 줄이기 위해 **100회 반복 평균**을 측정하였다. 또 입력 상태에 따른 차이를 확인하기 위해 **이미 정렬된 입력**에 대한 추가 실험을 수행하였다.

---

## 2. 구현 내용

### 2.1 병합 정렬

구간을 항상 가운데에서 둘로 나누어 각각 재귀적으로 정렬한 뒤, 두 정렬된 부분을 임시 배열 `temp`에 병합하고 원래 배열로 다시 복사한다. 임시 배열은 정렬을 시작할 때 `n`개 크기로 한 번만 할당한다.

### 2.2 퀵 정렬

피벗 선택만 다르고 분할은 세 방법 모두 같은 Lomuto 분할을 사용한다. 선택한 피벗을 구간의 마지막으로 옮긴 뒤, 피벗 이하인 원소를 앞쪽으로 모으고 피벗을 경계 위치에 놓는다.

| 방법 | 피벗 선택 |
|---|---|
| First | 현재 구간의 첫 번째 원소 |
| Random | 분할할 때마다 현재 구간의 무작위 위치 |
| Median-of-Three | 첫 번째, 가운데, 마지막 원소 중 크기가 가운데인 값 (2~3회 비교) |

### 2.3 난수 생성과 재현성

C 표준 `rand()`는 `RAND_MAX`가 플랫폼마다 다르다. Windows(MSVC)에서는 32,767이어서 0~1,000,000 범위를 고르게 만들 수 없다. 그래서 splitmix64 의사난수 생성기를 직접 구현하여 데이터 생성과 무작위 피벗 선택에 사용하였다.

시드를 `SEED`(기본값 `20261108`)로 고정했으므로 **비교 횟수, 이동 횟수, 메모리 값은 어느 환경에서 실행해도 똑같이 재현**된다. 실행 시간만 환경에 따라 달라진다.

### 2.4 정렬 검증

모든 정렬 결과에 대해 오름차순 여부를 검사하고, 네 알고리즘의 결과 배열이 서로 완전히 같은지도 `memcmp`로 확인하였다. 하나라도 실패하면 프로그램은 오류를 출력하고 종료한다. 6가지 크기 × 4가지 알고리즘 × 100회의 모든 정렬이 통과하였다.

## 3. 측정 기준

### 3.1 비교 횟수

| 알고리즘 | 포함하는 비교 |
|---|---|
| 병합 정렬 | 병합 과정에서 두 부분 배열의 원소끼리 비교한 횟수 |
| 퀵 정렬 | 분할 과정에서 원소와 피벗을 비교한 횟수 |
| Median-of-Three | 위에 더해, 중앙값을 결정하기 위한 비교 |

인덱스 비교, 반복문 종료 조건, 무작위 위치 생성, 배열 복사, 데이터 생성은 제외하였다.

### 3.2 실행 시간

- 같은 원본의 복사본 50개를 **측정 전에 미리 준비**하고, 정렬 50회만 연속으로 측정한 뒤 1회 평균을 구했다.
- 따라서 데이터 생성, 배열 복사, 정렬 검증, 결과 출력 시간은 측정에서 제외된다.
- `clock()`은 해상도가 낮아(Windows는 1ms) 작은 데이터를 1회만 재면 `0`이나 `1`로 나올 수 있다. 50회를 묶어 측정하여 이 문제를 피했다.
- 병합 정렬의 임시 배열 `malloc`/`free`는 병합 정렬이 반드시 필요로 하는 작업이므로 측정에 포함하였다. 별도로 측정한 결과 80KB 할당·해제는 1회에 약 0.00002ms로, 정렬 시간(약 2ms)에 비해 무시할 수 있는 수준이었다.

### 3.3 추가 메모리

원본 배열과 정렬용 복사 배열은 모든 알고리즘에 공통이므로 제외하고, **두 알고리즘에 같은 기준**을 적용하였다.

```text
추가 메모리 = 보조 배열 크기 + 최대 재귀 깊이 × 8 bytes
```

- **보조 배열**: 병합 정렬은 임시 배열 `n × sizeof(int)`, 퀵 정렬은 0
- **재귀 1단계당 8바이트**: 재귀 호출 한 단계가 나중에 처리할 구간 정보 `(low, high)`, 즉 `int` 2개(`sizeof(Range)`)를 기억해야 한다고 보았다. 재귀 대신 명시적 스택을 쓸 때 저장해야 하는 정보와 같은 양이다.
- **최대 재귀 깊이**: 첫 호출을 1단계로 보고, 크기가 1 이하라서 바로 반환하는 호출까지 포함해 가장 깊었던 단계를 기록하였다.

실제 함수 호출 프레임에는 복귀 주소, 다른 매개변수, 레지스터 저장 공간 등이 더 들어가므로 실제 스택 사용량은 이보다 크고 컴파일러마다 다르다. 따라서 이 값은 알고리즘이 논리적으로 필요로 하는 최소 공간이다. 두 알고리즘에 같은 기준을 적용했으므로 서로 비교하기에는 공정하다.

### 3.4 분석용 추가 지표

실행 시간의 원인을 분석하기 위해 비교 횟수 외에 다음 값도 기록하였다.

- **이동 횟수**: 데이터 대입 1회를 1로 계산한다. 퀵 정렬의 교환은 임시 변수를 거치므로 3회로 계산하였다.
- **호출 횟수**: 재귀 함수가 호출된 총횟수

## 5. 결과 분석

### 5.1 데이터 크기 증가에 따른 변화

100회 평균 비교 횟수를 기준으로, 데이터 크기가 늘 때 비교 횟수가 몇 배로 늘었는지 계산하면 다음과 같다.

| 크기 변화 | Merge | Quick (First) | Quick (Random) | Quick (Median3) | `n log n` 예상 | `n²` 예상 |
|---|---:|---:|---:|---:|---:|---:|
| 1,000 → 2,000 | 2.23배 | 2.26배 | 2.28배 | 2.21배 | 2.20배 | 4배 |
| 2,000 → 4,000 | 2.21배 | 2.22배 | 2.18배 | 2.19배 | 2.18배 | 4배 |
| 4,000 → 8,000 | 2.19배 | 2.21배 | 2.21배 | 2.18배 | 2.17배 | 4배 |
| 8,000 → 16,000 | 2.17배 | 2.18배 | 2.19배 | 2.17배 | 2.15배 | 4배 |
| 16,000 → 20,000 | 1.28배 | 1.28배 | 1.29배 | 1.28배 | 1.28배 | 1.56배 |

네 알고리즘 모두 데이터가 2배가 될 때 비교 횟수가 4배가 아니라 2.2배 정도로 늘었다. 이는 `n log n`의 예상 증가율과 거의 같으므로, 무작위 입력에서 모두 `O(n log n)`으로 동작하였다. 실행 시간도 4.1에서 크기가 2배가 될 때 약 2.1~2.4배로 늘어 같은 경향을 보였다.

비교 횟수를 `n log₂ n`으로 나누면 병합 정렬은 0.87~0.91, 퀵 정렬은 1.09~1.20이었다. 증가 속도(차수)는 같고, **앞에 붙는 상수만 병합 정렬이 더 작다**는 뜻이다.

### 5.2 비교 횟수: 병합 정렬이 가장 적은 이유

100회 평균에서 병합 정렬은 모든 크기에서 가장 적게 비교하였다. Median3보다 18.1~19.9%, First보다 20.5~23.1% 적었다.

**(1) 병합 정렬은 분할이 항상 완벽하게 균형적이다**

병합 정렬은 값과 관계없이 항상 가운데에서 나누므로 재귀 깊이가 `⌈log₂ n⌉ + 1`로 고정된다. 4.2에서 병합 정렬의 최대 깊이는 모든 시행에서 11, 12, …, 16으로 정확히 이 값이었다. 반면 퀵 정렬은 피벗이 구간을 정확히 반으로 나누는 경우가 드물어, 크기 20,000에서 최대 깊이가 First·Random 약 34, Median3 약 26이었다. 각 원소가 거치는 단계 수가 많을수록 비교도 많아진다.

**(2) 병합은 한 쪽이 먼저 끝나면 비교를 멈춘다**

길이 `m`인 구간을 병합할 때 비교는 최대 `m - 1`번이고, 한쪽 부분 배열이 먼저 바닥나면 나머지는 비교 없이 복사된다. 반면 퀵 정렬의 분할은 피벗을 제외한 모든 원소를 반드시 한 번씩 비교하므로 항상 `m - 1`번이다.

**(3) Median3가 세 피벗 중 가장 적었던 이유**

세 원소의 중앙값은 극단값이 될 확률이 낮아 분할이 더 균형적이다. 크기 20,000에서 Median3의 최대 깊이(25.8)와 호출 횟수(22,894.9)는 First(33.9, 26,668.4)보다 확실히 작았다. 중앙값을 정하는 비교가 추가되지만, 분할 비교가 줄어든 효과가 더 커서 전체 비교 횟수는 크기 20,000에서 First보다 약 6% 적었다. First와 Random은 무작위 입력에서 첫 원소 자체가 무작위 값이므로 사실상 같은 결과를 보였다.

### 5.3 실행 시간: 비교가 더 많은 퀵 정렬이 더 빠른 이유

4.1에서 병합 정렬은 모든 크기에서 Quick (Median3)보다 20.5~42.0% 느렸다. 비교 횟수는 병합 정렬이 약 19% 적은데도 시간은 오히려 더 걸렸다. 크기 20,000에서 비교 1회당 시간을 계산하면 병합 정렬은 약 9.0ns, Quick (Median3)는 약 6.1ns였다. **비교 1회에 딸린 부가 작업이 병합 정렬에서 더 많다**는 뜻이다.

**(1) 병합 정렬은 모든 원소를 단계마다 두 번씩 옮긴다**

병합 정렬은 각 단계에서 모든 원소를 `temp`에 쓰고 다시 원래 배열로 복사한다. 그래서 이동 횟수가 입력과 관계없이 고정되어 있다 (크기 1,000에서 100회 모두 정확히 19,952회). 반면 Lomuto 분할은 피벗보다 큰 원소는 제자리에 둔다. 그 결과 Median3의 이동 횟수(501,428.8)는 병합 정렬(574,464)보다 약 13% 적었다.

**(2) 병합 정렬은 원소 하나를 처리할 때 반복문을 두 번 거친다**

병합 정렬은 원소마다 병합 반복문에서 두 개의 조건(`i <= mid && j <= right`)을 검사하고, 복사 반복문을 한 번 더 돈다. 퀵 정렬의 분할은 반복문 하나에서 비교와 교환을 끝낸다.

**(3) 병합 정렬의 함수 호출이 더 많다**

병합 정렬은 크기 1인 구간까지 모두 나누므로 호출 횟수가 정확히 `2n - 1`이다 (20,000에서 39,999회). 퀵 정렬은 피벗 자리가 확정되어 다음 호출에서 빠지므로 호출 횟수가 First 약 26,668회, Median3 약 22,895회로 더 적었다.

**(4) 병합 정렬은 두 배열을 오간다**

퀵 정렬은 원래 배열 하나 안에서만 읽고 쓰지만, 병합 정렬은 원래 배열과 `temp`를 번갈아 읽고 쓴다. 다룰 메모리가 두 배이므로 CPU 캐시 효율 면에서도 불리하다.

**최적화를 켜도 결과는 같았다**

`-O2`로 컴파일하면 크기 20,000에서 병합 정렬 1.29ms, Quick (Median3) 1.01ms로 둘 다 빨라졌지만 병합 정렬이 여전히 약 27% 느렸다. 따라서 이 차이는 최적화를 하지 않아서 생긴 것이 아니라 알고리즘 구조에서 나온 차이이다.

**Random이 퀵 정렬 중 가장 느렸던 이유**

Random은 비교 횟수가 First와 비슷한데도 4.1의 모든 크기에서 퀵 정렬 중 가장 느렸다. 분할할 때마다 64비트 곱셈과 나눗셈(`%`)으로 난수를 만들기 때문이다. 이 비용은 측정 기준상 비교 횟수에는 들어가지 않지만 실행 시간에는 포함된다.

### 5.4 메모리: 병합 `O(n)` 대 퀵 `O(log n)`

크기 20,000에서 병합 정렬은 80,128바이트, 퀵 정렬은 208~280바이트를 사용하여 약 290~385배 차이가 났다.

- **병합 정렬**: 임시 배열이 `n`에 비례한다. 데이터가 2배가 되면 메모리도 정확히 약 2배가 된다 (4,088 → 8,096 → 16,104 …).
- **퀵 정렬**: 배열 안에서 자리를 바꾸므로 보조 배열이 필요 없고, 재귀 깊이만큼의 공간만 쓴다. 데이터가 20배(1,000 → 20,000)가 되어도 메모리는 174 → 271바이트(First 평균)로 약 1.6배만 늘었다. 이는 `log n`에 비례하는 증가이다.

### 5.5 입력 상태에 따른 차이: 이미 정렬된 입력

4.3의 결과는 두 알고리즘의 "안정성"(입력에 따라 성능이 흔들리지 않는 정도) 차이를 분명하게 보여준다.

- **병합 정렬은 오히려 빨라졌다.** 크기 1,000에서 비교 횟수가 8,704.5회(무작위 평균)에서 5,044회로 줄었다. 정렬된 입력에서는 왼쪽 부분이 항상 먼저 바닥나므로, 길이 `m`인 구간의 병합 비교가 `m/2`번으로 줄어들기 때문이다. 이론값 `(n/2) log₂ n ≈ 4,983`과도 거의 같다. 분할 방식이 고정되어 있으므로 최악의 경우에도 `O(n log n)`이 보장된다.
- **Quick (First)는 `O(n²)`으로 무너졌다.** 크기 2,000 → 4,000에서 비교 횟수가 3.99배로 늘었다. 정렬된 구간의 첫 원소는 항상 최솟값이라서 구간이 한 칸씩만 줄어들기 때문이다. 실행 시간은 병합 정렬보다 약 38배(4,000 기준) 느렸다.
- **메모리도 역전되었다.** First의 재귀 깊이가 `n`에 가까워져 추가 메모리가 31,896바이트(4,000 기준)가 되었다. 병합 정렬(16,104바이트)보다 커진 것이다. 실제 함수 프레임은 8바이트보다 훨씬 크므로, 실제로는 이보다 더 많은 스택을 쓴다.
- **Random과 Median3는 무너지지 않았다.** Random은 입력 순서와 관계없이 피벗을 고르므로 무작위 입력과 비슷한 성능을 유지하였다. Median3는 정렬된 구간의 가운데 원소가 정확한 중앙값이 되므로 퀵 정렬 중 가장 적게 비교하였고, 실행 시간은 네 알고리즘 중 가장 빨랐다.

## 6. 결론

| 기준 | 가장 우수한 알고리즘 | 근거 |
|---|---|---|
| 비교 횟수 | 병합 정렬 | 항상 완벽한 균형 분할, 퀵 정렬보다 약 18~23% 적음 |
| 실행 시간 (무작위 입력) | 퀵 정렬 (Median3, First) | 이동·호출·반복문 부담이 적음. 병합 정렬은 Median3보다 약 20~42% 더 오래 걸림 |
| 추가 메모리 | 퀵 정렬 | `O(log n)` 대 `O(n)`, 20,000에서 약 290배 이상 차이 |
| 최악의 경우 보장 | 병합 정렬 | 입력과 관계없이 `O(n log n)`, 정렬된 입력에서 오히려 빨라짐 |

- 네 알고리즘 모두 무작위 입력에서 `O(n log n)`으로 동작했지만, 차수가 같을 때는 **상수와 부가 작업**이 실제 성능을 결정하였다.
- **비교 횟수가 적다고 더 빠른 것은 아니다.** 병합 정렬은 비교가 가장 적었지만, 모든 원소를 단계마다 두 번씩 옮기고 두 배열을 오가는 비용 때문에 퀵 정렬보다 느렸다.
- 퀵 정렬의 성능은 피벗 선택에 크게 좌우된다. First는 정렬된 입력에서 시간과 메모리가 모두 무너졌고, Median3는 무작위·정렬 입력 모두에서 퀵 정렬 중 가장 균형 잡힌 결과를 보였다.
- 따라서 메모리가 넉넉하고 최악의 경우에도 일정한 성능이 중요하다면 병합 정렬이, 평균 속도와 적은 메모리가 중요하다면 Median-of-Three 같은 좋은 피벗 전략을 쓴 퀵 정렬이 적합하다.
